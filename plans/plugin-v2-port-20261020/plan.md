# Plan — Port the CodeRelay OpenCode plugin to the V2 plugin API

> **Status:** active
> **Started:** 2026-10-20 00:13
> **Subject:** Port the CodeRelay OpenCode plugin — both its server plugin and its TUI pairing screen — from the V1 plugin/SDK API to the V2 plugin API so it loads and runs under OpenCode v2.0.32.
> **Layout:** subfolder pattern

## Context

> Why is this being done? What prompted it? What is the intended outcome?

- Prompted by: the CodeRelay plugin is absent from the OpenCode plugin list. The runtime is OpenCode **v2.0.32** (upgraded from V1), and V2's plugin API is one of its three intentional breaking changes. The V2 documentation is explicit: "V1 plugin implementations do not run in V2. Moving a file or renaming its config entry is not enough."
- Goal: the plugin loads, registers and behaves exactly as it did on V1 — including the TUI pairing screen — on the V2 plugin and client surface, so the mobile companion works again.
- Outcome: a non-builtin active plugin entry in the V2 registry for this location, a working `CodeRelay: Pair device` QR modal, unchanged gateway/pairing/allowlist behaviour, and a package free of `@opencode-ai/*` dependencies.

Two independent defects were confirmed; both block the plugin:

1. **Config path (already corrected in the worktree, uncommitted).** `opencode.jsonc` previously pointed at `file:///home/dexm76/projects-personal/CodeRelay/packages/opencode-plugin/src/index.ts` — a POSIX file URL that fails on Windows. `~/.local/share/opencode/log/opencode.log` records `ERROR "failed to reload plugins" cause="Cause([Die(TypeError [ERR_INVALID_FILE_URL_PATH]: File URL path must be an absolute path)])"`. A later attempt pointed at `src/index.ts` and produced `WARN "configured plugin path must be a directory"`. The current `./packages/opencode-plugin` directory form is the shape the runtime accepts.
2. **V1 plugin implementation (this plan).** Both entrypoints are the V1 contract. `packages/opencode-plugin/src/index.ts:40` is `const plugin: Plugin = async (input): Promise<Hooks> => {`, returning V1's `event` (`:117`), `dispose` (`:122`) and `tool` map (`:127`), built with the V1 `tool()` helper (`:1`, `:128`). `packages/opencode-plugin/src/tui.tsx:6` imports the V1 TUI types from `@opencode-ai/plugin/tui`. The live registry proves nothing of ours is loaded: `opencode api get '/api/plugin?location[directory]=G:\projects-personal\code-relay'` returns **zero non-builtin entries** — every returned entry is `"source":{"type":"builtin"}`. (The total count varies between runs and is deliberately not cited; the load-bearing fact is the zero.)

A third, related defect: the TUI extension is **already unloaded** on V2. `tui.jsonc` at the repository root is `{ "plugin": ["./packages/opencode-plugin/src/tui.tsx"] }`, which is V1 terminal-client configuration. V2 moved terminal configuration to the single global `~/.config/opencode/cli.json`; that file has four top-level keys (`$schema`, `theme`, `terminal`, `attention`) and **no `plugin` entry**, and the migration guide states "Project-local client configuration is not migrated because V2 client configuration is global." So the pairing screen is absent on V2 today and this plan restores it.

## Design decisions

- **Port the TUI extension as well as the server plugin** — user decision recorded 2026-10-20, reversing the earlier "server plugin only" choice. Evidence that changed the call: `tui.tsx:6` imports `@opencode-ai/plugin/tui`, so the "no `@opencode-ai` remains" goal cannot hold while `tui.tsx` is unported; and `tui.jsonc` is V1 terminal config that V2 does not read, so the pairing screen is already absent and would otherwise be a silent regression of the story's AC2. Simplest alternative considered: keep `@opencode-ai/plugin` as a dev-only type dependency and defer the TUI port; rejected because it leaves the pairing screen broken and keeps a V1 package in the tree.
- **Delete `tui.jsonc` rather than migrate it** — the V2 CLI guide states that exporting `./tui` beside `.` from `package.json` gives automatic loading, and our `package.json:8` already exports `"./tui": "./src/tui.tsx"`. V2 reads terminal plugins from the global `cli.json` only for CLI-only packages. Simplest alternative: add the plugin to `~/.config/opencode/cli.json`; rejected because it would configure a machine-global file for a project-local plugin and would not load the server entry.
- **Bump `@opentui/*` peers to `>=0.5.17`**, corrected 2026-10-20 after Warden 🔒 (Dependency Warden) `[ADVISORY]` finding 1. The binding constraint is `@opencode/plugin@2.0.32`'s **own** `peerDependencies`, which declare `@opentui/core: '>=0.5.17'` and `@opentui/solid: '>=0.5.17'`; the previously planned `>=0.5.8` is out of range for the SDK we pin. The current `/build/plugins/cli` page shows `>=0.6.6` because it tracks the `@opencode/plugin@2.1.x` line — it moved from `>=0.5.8` during this work, which is why an earlier read of it is not wrong so much as stale. Since this plan pins `2.0.32`, we match `2.0.32`'s floor and deliberately do **not** pull OpenTUI 0.6 breaking changes into the `T3` port. The guide never names `@opentui/keymap`, so raising it to `0.5.17` too is an **alignment choice across the OpenTUI set** and must not be cited to the guide. Simplest alternative: match the guide's `>=0.6.6`; rejected because that pulls OpenTUI 0.6 API changes into a port whose whole point is minimal blast radius. `hipótesis:` a future re-pin to `@opencode/plugin@2.1.x` will cascade the floor to `>=0.6.6` — re-pin only on a runtime upgrade.
- **Port shapes stay structurally declared, but `gateway.ts` joins the manifest** — **superseded 2026-10-21 when the user directed "fix all".** The original design froze `gateway.ts` (724 lines, 1972-line suite) to contain the blast radius. Bastion 🧱 (Backend & Scripts Architect) then found `allowlist.ts:391-395` returning a transport failure as `AllowlistError`, which `gateway.ts:497/:503` cannot distinguish from a policy denial. `knowledge/agents.md` **Clean architecture** requires nonconforming planned files to be reworked in this plan "including necessary supporting files", with **no legacy exemption**, so freezing `gateway.ts` would ship a known rule violation against the plan's own gate. The minimal error-channel edit is now in scope. What is preserved: `projectActivityPart`'s exported signature and redaction behaviour, and `AllowedActionResult`'s shape — the gateway's *routing* logic does not change, only how it handles a boundary failure.
- **Declare port shapes structurally instead of deriving them from `OpencodeClient`** — required by `knowledge/agents.md:49-59` **Clean architecture**. Any framework type derivation moves to one infrastructure adapter.
- **Keep the plugin at `packages/opencode-plugin/` and load it from `opencode.jsonc`** — user decision recorded 2026-10-20.
- **Do not ship a dual V1/V2 entrypoint** — the runtime here is v2.0.32 only, so the migration guide's `setup()` + `server()` shape would double the surface to maintain for a runtime that is never used.
- **Use PowerShell `Select-String`, not `rg`, in every verify command** — `Get-Command rg` raises `CommandNotFoundException` in the agent shells, so an `rg` verify command is not runnable by its declared executor.
